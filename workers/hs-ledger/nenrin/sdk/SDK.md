# nenrin_verify.mjs : verify a NENRIN provenance bundle yourself, in one file

One file, zero dependencies (Node built-ins only). Copy it into your project and check a NENRIN evidence bundle
offline, with no trust in the operator. This is the endpoint of "verify me, do not trust me": you do not take
HORIZON SHIELD's word for anything, you recompute every hash and signature on your own machine.

## Install (npm) or vendor the one file
    npm install nenrin-verify        # then: npx nenrin-verify bundle.json
or copy the single file nenrin_verify.mjs into your project. Zero dependencies either way.

## Use it
    node nenrin_verify.mjs bundle.json      # prints the provenance report; exit 0 if accepted, 1 if refused

or import it:
    import { verifyProvenance, consumeEvidence, publicKeyFromDidKey } from "./nenrin_verify.mjs";

A bundle is { task_id, observations?, grant?, intent?, receipt | receipts?, require_signatures? } whose
identifiers (witness_id, hop.from, caller_id, provider_id) are did:key strings. The CLI resolves them to Ed25519
public keys from the identifiers themselves, with no network and no key server.

## What it checks (the whole graph, one call)
- delegation: R1 witness independence, R2 recompute, R3 hop continuity, R4 disagreement preserved (never
  collapsed to the favorable verdict), witness_sig and edge_sig
- execution: E1 authorized action equals executed action, E2 outcome reconciliation (equivocation fail-closed),
  E3 grant binding, caller_sig and provider_sig, strict RFC3339 UTC window
- evidence: the outcome's pointer to an independently checkable artifact (bitcoin_tx, ledger_record, ...)
- cross-layer: every record shares one task_id; an observation's digest-bound link names the reconciled receipt
- consumeEvidence / candidateEvidenceSet: a compact projection a trust engine or orderer reads, with no score
  and no allow or deny

## The guarantee, and its honest limit
The report carries establishes and does_not_establish. Signatures prove WHO asserted and the linkage, not that
any assertion is TRUE; there is no side-effect oracle, so no executed action is proven to have happened in the
world, and R1 proves structural distinctness, not unaffiliation. Verification is free and open by design: the
trust comes from you checking, not from anyone paying.

## How this file is built and why you can trust the copy
It is generated by build_sdk.mjs by concatenating the pinned nenrin modules and stripping internal imports;
re-running is deterministic. nenrin_verify.test.mjs runs identical inputs through this single file and through
the original modules and asserts the verifyProvenance report and the consumeEvidence projection are byte for
byte identical, then runs the CLI on a real did:key bundle offline. Run: node nenrin_verify.test.mjs

## tsugi_verify.mjs (0.2.0): verify a TSUGI recovery chain yourself, in one file

TSUGI (継) is the second pillar: proof of recovery. A chain is drift records, one proposal from a closed repair
catalog, an authorization signed by the operator's Ed25519 key, an execution, and a re-verification, hash-linked.
The re-verification may carry a random witness draw (a Bitcoin block hash, the public pool's hash and the record's
hash as the seed) and the drawn witnesses' signed observations.

    npx tsugi-verify chain.json                                            # lenient: hashes, links, order, catalog
    npx tsugi-verify chain.json --operator-key <base64 Ed25519 public key>  # strict: the operator must have signed the authorization
    npx tsugi-verify chain.json --fetch-operator-key https://gate.horizonshield.dev
    npx tsugi-verify chain.json --operator-key ... --pool pool.json --q 2 --k 3 --beacon <block hash> --require-commitment --anchor-height H --anchor-hash <hash>

What the flags mean: --pool is the public witness pool the draw was made from (the verifier recomputes the draw and
refuses draw_mismatch); --q is how many drawn, signed, distinct-domain witnesses must have observed the expected
state; --k is the policy draw size (an operator may not shorten the draw); --beacon is the block hash you fetched
yourself from your own chain source; --require-commitment demands that the draw's subject was anchored on the
ledger before the beacon block (commit-then-reveal), with --anchor-height and --anchor-hash being what you verified
from that ledger entry's OpenTimestamps proof. Every refusal has a code and an English sentence. The report ends
with does_not_establish. A real chain to try: workers/hs-ledger/nenrin/recovery-v0/incident_20260920_resign_chain.json
(operator key served at https://gate.horizonshield.dev/keys/operator.json, anchored as JIDEC entry 50).
