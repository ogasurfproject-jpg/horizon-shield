## 3. 門の instant coordinate に発見 3 件(論文2 の草稿中に判明。詳細と直し方は ops/gate_history_coordinate_20260906.md)

worker.js を読んで出た。全部 0.3.0 以降の本番の穴で、優先は A → C → B。

- A. **履歴が導出ブロックを落とす。** runCheck() の判定には coordinate_derivation が載る(1486 行)が、履歴に残す summarise()(2375 行〜)がそれを拾っていない。だから /history export(ring 原料、register アーカイブ、verify_beacons と C15 の入力)には derived beacon が構造的に現れず、C15 は「無い」で PASS していた = 測れていない。直し: summarise() に coordinate_derivation を 1 フィールド足す(verify_beacons.py が読む形: derived / window_id / salt_commitment / salt_created_at / beacon{height,block_hash} / day_in_window / tool_measured / fallback)。既存エントリは触らない。redteam_gate.mjs に 1 本。
- C. **salt が block の後に作られる。** coordinate()(nenrin_instant.js 134 行〜)は掃引の頭で windowState()(無ければその瞬間に salt 作成、salt_created_at = now)→ 直後に beacon()(tip - 6、約 1 時間前の block)。追補 instants v1 は「commitment は窓の開始高さより下に錨打ち、beacon は salt の後の block」で、verify_beacons.py もその向きで検査し逆順を FALSIFIED("SALT AFTER BLOCK: the gate could have chosen the salt knowing the hash")にする。つまり導出できても自分の検証器に落とされる。直し: (i) salt は窓の頭(木曜 00:00 UTC、window_id = epoch 日数 / 7)に作る(cron `0 0 * * 4` を足すか、18:00 掃引で次の窓の salt を先に作る)。(ii) beacon は salt_created_at より後に採掘された block に限る(block の timestamp を読んで確認、古ければその窓の初回は fallback として正直に落とす)。(iii) commitment を作った瞬間に公開(GET /nenrin/window/{wid})、可能なら ledger witness 経路で日次バッチに載せて Bitcoin 錨打ち(addendum の anchor.commit_height を満たす)。
- B. **一致判定が tip ずれで落ちる。** beacon()(103〜119 行)は各源で `h = tip - BEACON_LAG(6)` を計算し `good.every(x => x.height === good[0].height && ...)`。二つの explorer の tip が 1 ブロックずれるのは平常なので高さが一致せず fallback になる(9/5 18:00Z の初回掃引が legacy に落ちた原因はこれの可能性が高い。/sweep/last が legacy schedule と記録)。freshness v3.2/v3.3 で閉じた「遅れた源の拒否権」「基準 tip は quorum 番目」が本番に持ち込まれていない。直し: 両源の tip を読み、基準高さ = min(tip) - 6(または quorum 番目の tip - 6)を 1 つ決め、その同じ高さの hash を全源から取って hash の一致だけを要求する。
